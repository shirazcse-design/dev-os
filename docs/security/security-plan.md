# ContractIQ — Security Plan

Generated by the `/security-foundation` pass. Covers auth, API validation, rate
limiting, prompt injection, token/usage limits, chat authorization, file
upload security, and environment variable hygiene, per the requirements in
`skills/security-foundation/SKILL.md`.

---

## Issues found and fixed

| # | Issue | Where | Fix |
|---|---|---|---|
| 1 | Rate-limit counters were user-writable. `rate_limits` (old table) had `insert`/`update` RLS policies scoped to `auth.uid() = user_id`, and the app queried/wrote it using the caller's own session (anon-key client). A malicious client could call the Supabase REST API directly with their own JWT and reset or fabricate their own `request_count`, bypassing extract/chat rate limits entirely. | `lib/api/rateLimit.ts` (deleted), `docs/specs/supabase-schema.sql` `rate_limits` policies | Replaced with `lib/security/rateLimiter.ts`, a sliding-window limiter over a new `rate_limit_events` table that is **service-role only** — RLS is enabled with zero user-facing policies, so no session (anon or authenticated) can read, insert, or delete rows in it. |
| 2 | Chat authorization was ownership-only. `POST /api/chat` fetched the contract scoped to `user_id` but never checked `contracts.status`, so a user could call the API directly (bypassing the client-side "chat tab disabled until completed" gate) and chat against a contract still `uploaded`/`processing`/`error`. | `app/api/chat/route.ts` | Added an explicit `status === 'completed'` check via `verifyContractOwnership()`, returning `409 CONTRACT_NOT_READY` otherwise. |
| 3 | No file-content validation on upload. Only `file.type` (a browser-supplied, spoofable header) and size were checked; a non-PDF file renamed to `.pdf` with a forged `Content-Type` would pass straight through to the PDF parser. | `app/api/contracts/route.ts` | Added `validateFileUpload()` (`lib/security/inputValidator.ts`): blocklist → allowlist extension → MIME → size → **magic-byte check** (`%PDF` header), in that order, before the file is ever parsed. |
| 4 | No login rate limiting. `signInWithPassword` was called client-side directly against Supabase Auth with no app-level throttle, and there was nowhere server-side to add one. | `app/(auth)/sign-in/page.tsx` | Added `POST /api/auth/login`, which rate-limits by client IP (10/min) *before* checking credentials, then signs in server-side so the session cookie is set via the `@supabase/ssr` server client. Sign-in page now calls this route instead of the client SDK directly. |
| 5 | Custom key-term names were interpolated directly into the extraction **system** prompt (`customTerms.join(', ')` in `lib/prompts/extraction.ts`), unlike contract text, which is always sent as untrusted `user`-role content. An attacker-supplied term name could attempt a prompt injection at the system-prompt level. | `app/api/extract/route.ts`, `lib/prompts/extraction.ts` | Every custom term is now checked with `sanitizeForLLM()` and the request rejected (`400 PROMPT_INJECTION`) before any OpenAI call if one matches a known injection pattern. Also hardened the extraction and chat system prompts to explicitly instruct the model to treat contract text as untrusted content, never as instructions. |
| 6 | No prompt-injection screening on chat messages. A user's raw message went straight into the chat completion call. | `app/api/chat/route.ts` | `sanitizeForLLM()` now runs on every incoming chat message before it's persisted or sent to the model; a match returns `400 PROMPT_INJECTION` and the message is never saved or sent to OpenAI. |
| 7 | No authenticated-user redirect away from `/sign-in` / `/sign-up`. A logged-in user hitting either page saw the auth form instead of being redirected to `/dashboard`. | `middleware.ts` | Added an `AUTH_PREFIXES` check that redirects authenticated users on those two routes to `/dashboard`. |
| 8 | Sign-out went through the browser Supabase client only (`supabase.auth.signOut()` client-side), with no server-side cookie clear. | `components/shared/Header.tsx` | Added `POST /api/auth/logout`, which calls `supabase.auth.signOut()` server-side; the client now calls this route instead. |
| 9 | Duplicated, inconsistent auth-check boilerplate (`const { data: { user } } = await supabase.auth.getUser(); if (!user) return unauthorized()`) repeated in every route, with no single place to audit. | All `app/api/*/route.ts` | Centralized into `requireAuth()` (`lib/security/authGuard.ts`); every route now uses the same helper, so a future auth-check change or bug fix only needs to happen once. |
| 10 | No HTTP security headers at all — no `headers()` export existed in `next.config.mjs` (and nothing in `middleware.ts`, no `netlify.toml`/`vercel.json`), so responses carried no `X-Frame-Options`, `X-Content-Type-Options`, CSP, or HSTS. Not covered by the original `/security-foundation` skill pass (it doesn't mention HTTP response headers). | `next.config.mjs` | Added `async headers()` returning `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `Strict-Transport-Security`, and a `Content-Security-Policy` scoped to `'self'` plus the Supabase project origin (derived from `NEXT_PUBLIC_SUPABASE_URL`, both `https://` and `wss://` for Realtime). Verified via `curl` and live in-browser (dashboard, PDF text view, chat incl. Realtime websocket) — headers present on every route, no console/CSP errors, no functional regression. |

None of the above were exploited in production — this is a pre-launch pass (Stage 7 of the project workflow), not an incident response.

## Controls implemented

### 1. Authentication & protected routes
- `middleware.ts` protects `/dashboard`, `/upload`, `/contracts` (redirect to `/sign-in?redirect=...` if unauthenticated) and now also redirects an authenticated user away from `/sign-in` / `/sign-up` to `/dashboard`.
- Login and logout now go through server routes (`app/api/auth/login`, `app/api/auth/logout`) so cookies are always set/cleared via the `@supabase/ssr` server client.
- **Manual action required** — verify/enable in the Supabase dashboard (not settable via API/code):
  - Email verification
  - Password reset flow
  - Session management / refresh token rotation
  - (Optional but recommended) CAPTCHA on sign-up, since sign-up itself is not yet rate-limited server-side — see Outstanding items.

### 2. API request validation
Every route validates its body with Zod before touching the database, per the existing (already-approved) convention in `docs/specs/api-infrastructure.md` — `400 VALIDATION_ERROR` for schema failures, `422` reserved for domain-level semantic failures (`TOO_MANY_CUSTOM_TERMS`, `SCANNED_PDF`, `TOKEN_LIMIT_EXCEEDED`, `PAGE_LIMIT_EXCEEDED`), consistent with the already-approved Stage 2 spec. `lib/security/inputValidator.ts` re-exports every schema from `lib/validation/schemas.ts` (now including `loginRequestSchema`) as the single place to look them up, plus `validateFileUpload()` for the one non-JSON input (the upload form's file field).

### 3. Rate limiting
`lib/security/rateLimiter.ts` — sliding window over `rate_limit_events`, service-role only.

| Action | Limit | Window |
|---|---|---|
| `auth` (login) | 10 | 1 minute |
| `chat` | 30 | 1 minute |
| `extract` | 5 | 1 hour |
| `upload` | 20 | 1 day |

All `429` responses set a `Retry-After` header (see `tooManyRequests()` in `lib/api/errors.ts`). The limiter fails **open** (allows the request, logs the error) if `rate_limit_events` is unreachable — e.g. before the migration below has been run — since every gated route including login depends on it, and a broken limiter must never mean a broken app.

### 4. Prompt injection protection
`lib/security/promptInjectionGuard.ts` — `sanitizeForLLM()` matches the required pattern set (ignore previous instructions, override your rules, reveal system prompt, print your instructions, expose env variables, show API keys, you are now a, act as, pretend you are, jailbreak, DAN mode, developer mode). Applied to:
- Every chat message, before persisting or calling the model (`app/api/chat/route.ts`).
- Every custom key-term name, before extraction (`app/api/extract/route.ts`) — this is the one place user text is embedded in a **system**-role prompt.

Contract text itself is *not* run through this blocklist (see Outstanding items for why), because it's large real-document text where the pattern set would produce false positives; instead both `lib/prompts/chat.ts` and `lib/prompts/extraction.ts` now explicitly instruct the model to treat contract text as untrusted content and never follow instructions embedded in it, and it is always sent as `user`-role content, never concatenated into the system prompt.

### 5. Token & usage limits
`lib/security/tokenLimiter.ts` — single place documenting every request-size ceiling (re-exporting the product-level, stricter values from `lib/config.ts` where they already exist, rather than defining a second, looser set):

| Limit | Value | Source |
|---|---|---|
| Max file size | 10 MB | `lib/config.ts` `MAX_UPLOAD_SIZE_MB` (matches storage bucket limit) |
| Max page count | 20 pages (product limit; security ceiling is 200) | `lib/config.ts` `MAX_PAGE_COUNT` |
| Max message length | 2000 chars (product limit, enforced by `chatRequestSchema`; security ceiling is 5000) | `lib/security/tokenLimiter.ts` `MAX_MESSAGE_LENGTH` |
| Max chat history sent to model | `MAX_CHAT_HISTORY` env var, default 100 (applied as an outer cap on top of the 10/20-turn classification-driven limits in `lib/prompts/chat.ts`) | `.env.example` |

### 6. Chat security
`lib/security/chatSecurity.ts` — `verifyContractOwnership()` (also checks `status === 'completed'`, enforced in the route) and `verifySessionOwnership()`. `app/api/chat/route.ts` and `app/api/chat/[sessionId]/messages/route.ts` both use these instead of inline queries. Ownership failures return `404`; a not-yet-completed contract returns `409 CONTRACT_NOT_READY`.

### 7. File upload security
`lib/security/inputValidator.ts` `validateFileUpload()` — blocklist (`.exe .js .mjs .cjs .php .zip .sh .bat .cmd .py .rb .ps1`) checked first, then allowlist (`.pdf` only — see Outstanding items re: `.docx`), MIME type, size, then a magic-byte check on the first 4 bytes (`%PDF`). Files are stored in the private `contracts` Supabase Storage bucket (already `public: false`) with signed URLs generated on demand at a 1-hour expiry (`app/api/contracts/[id]/route.ts`) — unchanged, already correct. Uploaded filenames are now sanitized before being used in the storage key.

### 8. Environment variable security
Verified: `OPENAI_API_KEY` and `SUPABASE_SERVICE_ROLE_KEY` have no `NEXT_PUBLIC_` prefix and are read only in server-only modules (`lib/openai/client.ts`, `lib/supabase/admin.ts`). `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` are the only public ones, both safe to expose. No secret is logged anywhere in the codebase (checked via grep for `console.log`/`console.error` near key/token/secret usage). `SUPABASE_SERVICE_ROLE_KEY` is used in exactly one place: `lib/supabase/admin.ts`'s `createAdminClient()`.

### 9. HTTP security headers
`next.config.mjs` `async headers()` applies to every route (`/:path*`):

| Header | Value |
|---|---|
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` |
| `Content-Security-Policy` | `default-src 'self'`; `connect-src` scoped to `'self'` + the Supabase project origin (`https://` and `wss://`, derived from `NEXT_PUBLIC_SUPABASE_URL`); `frame-ancestors 'none'`; `object-src 'none'`; see caveat below |

Verified with `curl -I` on both a page route and an API route, and live in-browser (dashboard, contract text view, chat including the Realtime websocket) — headers present everywhere, zero console/CSP errors, no functional regression.

## SQL to run in Supabase

Paste `supabase/rls-policies.sql` into the Supabase SQL Editor. It creates `rate_limit_events` (service-role only, no user-facing policies) and idempotently re-asserts RLS is enabled on every table. It does **not** duplicate the per-table CRUD policies already in `docs/specs/supabase-schema.sql` — those were audited in this pass and are correct as-is.

## Outstanding items

- **Sign-up is not rate-limited server-side.** `app/(auth)/sign-up/page.tsx` still calls `supabase.auth.signUp()` client-side. The skill's explicit deliverables were `app/api/auth/login` and `app/api/auth/logout` only; routing sign-up through a server endpoint too (to apply the same `auth` rate-limit bucket) would close this gap but was left out to avoid expanding scope beyond what was asked. Recommend enabling CAPTCHA on sign-up in the Supabase dashboard as a stopgap.
- **`sanitizeForLLM()` is not applied to contract text.** Deliberate — see "Prompt injection protection" above. The mitigation there is architectural (untrusted content is always `user`-role, never concatenated into the system prompt, and the model is explicitly told not to follow embedded instructions) rather than pattern-matching, since blocklisting real contract text would produce unacceptable false-positive rejections of legitimate uploads.
- **`.docx` is not supported**, despite being in the skill's example allow-list. This codebase has no DOCX parser (`lib/pdf/extractText.ts` is PDF-specific) — accepting the extension would let a file pass upload validation and then fail unpredictably at extraction. `validateFileUpload()` allows `.pdf` only. Add `.docx` to the allow-list only alongside an actual DOCX text-extraction path.
- **The old `rate_limits` table is not dropped**, only its user-facing policies are revoked (`supabase/rls-policies.sql`). Dropping it is a destructive schema change outside this pass's scope — drop it manually once you've confirmed nothing else references it.
- **`act as` / `pretend you are` in the injection pattern set are broad** and can false-positive on legitimate contract questions (e.g. "if I act as guarantor, what's my liability?"). Implemented as specified since the skill lists them explicitly; narrow the regex if false positives show up in practice.
- **CSP allows `'unsafe-inline'` (and `'unsafe-eval'` in dev) for `script-src`**, rather than a strict nonce-based policy. The App Router injects its hydration payload as an inline script with no nonce wired up; a stricter CSP would need per-request nonce generation added to `middleware.ts` and threaded through to any inline `<Script>` usage. Still meaningfully restricts `frame-ancestors`, `object-src`, `base-uri`, `form-action`, and `connect-src` to known origins — worth tightening `script-src` in a follow-up if a stricter policy is required (e.g. for a compliance audit).
